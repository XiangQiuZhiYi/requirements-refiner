# 需求收集与完善

把语雀、MasterGo 和用户补充整理为可审核、可追溯、可供后续开发引用的需求资料包。详细需求是唯一事实来源；引导文档负责解释需求并降低审核难度。

## 边界

- 只收集、核对、补全和修订需求。
- 不分析代码，不生成技术方案，不设计 API，不开始开发。
- 不回写语雀或 MasterGo。
- 不把通用经验或 AI 推断写成已确认需求。

## 检查环境

用户说“检查需求整理环境”或同义表达时，只做能力检查，不创建需求文档：

1. 枚举当前会话可调用的资料工具；工具由搜索机制延迟提供时，先搜索 Yuque、MasterGo、outline、section 和 DSL 等能力词。
2. 完整阅读 [MCP 工具能力解析](references/tool-resolution.md)，按工具尾名和描述判断能力，不依赖 MCP 服务器名称。
3. 报告语雀大纲、语雀正文导出、MasterGo 分区读取是否可用，并单独列出可选的语雀单篇读取和 MasterGo 完整 DSL 回退能力。
4. 缺失时只说明缺少的逻辑能力和影响，不要求用户把 MCP 重命名为固定名称。
5. 明确说明 npm 插件不保存 MCP 配置；检查结果只反映当前 Codex 会话。

## 输入

接受以下任意组合：

- 一个或多个语雀文档 URL；根文档可包含目录中的子文档。
- 一个或多个 MasterGo 短链接，或 `fileId`、`layerId`、`sourceLayerId`。
- 可选原图或截图的本地绝对路径。
- 可选需求名称、阶段名称和用户补充。

缺少需求名称时使用语雀根文档标题；缺少阶段时，只有来源明确写出“一期”“二期”等阶段才采用，否则使用“未分期”。

每次收到一组新的需求资料，都把它视为独立需求身份解析。不得从上一轮需求、相邻目录、历史对话中的其他需求继承需求名称、阶段或编号前缀。只有用户本轮明确指定，或本轮来源明确写出时，才能采用名称与阶段；来源未标阶段时必须使用“未分期”和 `PX` 编号前缀。

## 执行步骤

### 1. 确定输出目录

先仅根据本轮输入建立需求身份：

- 需求名称：用户本轮指定；否则取本轮语雀根文档标题。
- 阶段：用户本轮指定；否则取本轮来源明确阶段；两者都没有时使用“未分期”。
- 编号前缀：阶段明确时按阶段生成；“未分期”固定使用 `PX`。

生成或更新文件前，检查最终目录和编号前缀是否都能追溯到本轮输入。若只能从上一需求获得某个值，视为未提供并使用上述默认值，不得沿用。

以当前项目目录为根，输出到：

```text
docs/requirements/<需求名称>/<阶段>/
```

清理文件名中的路径分隔符和控制字符，但保留中文。不要覆盖同目录中的用户文件；更新已有需求包时只修改本技能管理的文档。

### 2. 收集并冻结资料

完整阅读 [资料采集规则](references/source-collection.md)。
开始调用外部资料工具前，完整阅读 [MCP 工具能力解析](references/tool-resolution.md)，按工具能力和尾名解析当前用户环境，不绑定 MCP 服务器名称。

- 语雀：使用当前环境中匹配 `yuque_get_doc_outline` 和 `yuque_export_docs_bundle` 能力的工具，先读取大纲，再读取正文、子文档、表格和资源链接；单篇文档可使用匹配 `yuque_get_doc_markdown_by_url` 的工具。
- MasterGo：使用当前环境中匹配 `mastergo_getDesignSections` 能力的工具获取分区清单，再按 `sectionIndex=0..totalSections-1` 读取全部分区；每批并发 3–5 个。只有该能力失败时才使用匹配 `mastergo_getDsl` 的回退工具。
- 不因分区同名、名称为空或节点数相同而跳过分区。
- 原图存在时同时分析全局图与局部细节；只有 DSL 时继续生成，但在资料限制和引导文档中明确说明。
- 在 `_sources/` 保存资料索引和规范化快照。记录来源编号、标题、URL、获取时间、范围、版本信息和读取限制。
- MasterGo 抓取时完整阅读 [UI 上下文缓存与交接](references/ui-context-handoff.md)，把每个成功分区的完整数据持久化到 `_sources/raw/UI-xx/`，不得只保留业务摘要。

### 3. 判断目录形态

完整阅读 [文档契约](references/document-contract.md)。

只在以下任一条件成立时拆分 UC：

- 语雀标题或正文明确标出 `UC`、`用例`及其名称或编号。
- 用户明确给出 UC 清单或要求按指定 UC 拆分。

MasterGo 页面、Frame、弹窗或 AI 对业务的理解都不能单独成为拆分依据。来源只明确阶段、未明确 UC 时生成单体需求，并增加“是否需要拆分 UC”待确认项。

单体需求：

```text
00-需求引导.md
01-详细需求.md
_sources/资料索引.md
```

多 UC 需求：

```text
00-需求引导.md
01-公共需求.md
UCxx-名称/需求引导.md
UCxx-名称/详细需求.md
_sources/资料索引.md
```

从 `assets/templates/` 复制最匹配的模板。不得复制模板中的示例占位内容到正式需求。

### 4. 整合需求

- 先分别提取语雀事实、MasterGo 可见事实和用户补充，再交叉核对，禁止直接混合总结。
- 覆盖背景、目标、范围、角色、流程、功能、字段、校验、交互、状态、权限、异常、边界和验收标准。
- 每条正式需求使用稳定编号和显式 HTML 锚点，例如：

```markdown
<a id="p1-uc01-fr001"></a>
### P1-UC01-FR001｜创建用户

- 状态：来源已确认
- 来源：[DOC-01-S003｜新增用户](../_sources/DOC-01.md#doc-01-s003)
```

- 编号类型使用 `FR`（功能需求）、`BR`（业务规则）、`AC`（验收标准）；公共规则使用 `P1-COM-*`。
- 未拆分 UC 的单体需求使用 `P1-REQ-*` 或 `PX-REQ-*`，不得为编号方便虚构 `UC01`。
- 状态只能是：`来源已确认`、`用户已确认`、`推断待确认`、`来源冲突`、`信息缺失`。
- AI 补充只能写入“推断待确认”或“待确认事项”，并说明缺失了什么证据。
- 语雀与 MasterGo 冲突时保留双方内容，不选择胜者；在引导文档中提出可回答的问题。
- 在规范化快照中按业务主题建立 `DOC-01-S001`、`UI-01-S001` 等稳定来源片段；详细需求优先链接来源片段，不使用快照行号定位。

### 5. 生成审核引导

单体需求使用根目录的 `00-需求引导.md` 完整说明需求。多 UC 需求使用两级引导：

- 根目录 `00-需求引导.md` 说明整体背景、范围、跨 UC 流程、公共规则和 UC 关系，只承担总览职责。
- 每个 `UCxx-名称/需求引导.md` 独立说明该 UC。必须按“功能点 1、功能点 2……”逐项阐述功能行为、参与者/入口、操作结果、关键规则、审核重点和未决问题；不能只列功能标题和链接。
- 重点样式放在每个功能点的需求描述正文中：选择性加粗业务对象、用户操作、选项、状态、数量限制、结果和权限边界。固定标签保持普通样式，避免标签比需求内容更抢眼。不得整段加粗或用样式掩盖来源状态。
- 每个功能点使用 `guide-point` 受管标记和一个审核状态。状态只允许 `未审核`、`理解一致`、`需要修改`、`存在疑问`；它不改变详细需求的事实状态。
- 用户可以按功能点确认，也可以用“UC05 全部理解一致”“除功能点 9 外都确认”等表达批量更新同一 UC。只有实际存在意见时才写 `用户意见`。
- 待确认问题由 AI 先标记 `阻塞开发`、`影响验收` 或 `可后补充`，用户可直接修正。

详细字段、异常和验收规则使用受管链接跳转，不复制全部详细需求，也不得把 UC 引导退化为纯目录。每个功能点至少链接一个稳定需求编号。插入以下独占行作为链接占位符：

```markdown
<!-- guide-point:P1-UC01-FR001 sync:pending -->
- 审核状态：未审核
- <!-- req-link:P1-UC01-FR001 -->
```

运行索引脚本后，该行会同时生成可移植的相对锚点链接和当前机器的绝对行号链接。不得把其他用户正文放在受管链接行上。

### 6. 建立索引并校验

在需求包根目录执行：

```bash
node <skill-dir>/scripts/build-requirement-index.mjs <需求包目录>
node <skill-dir>/scripts/validate-requirements.mjs <需求包目录>
```

第一条命令生成 `requirement-index.json` 并刷新受管链接；第二条命令检查编号、状态、来源、锚点、链接和审核项。修复所有错误后再交付；未解决问题可以保留，但必须汇总报告。

第一条命令同时生成可移植的 `requirement-package.json`，作为后续技术方案和开发读取需求文档、审核状态及冻结 UI 快照的统一入口。

详细需求与引导已经人工核对一致后，接受新的同步基线：

```bash
node <skill-dir>/scripts/build-requirement-index.mjs <需求包目录> --accept-guide-sync
```

同步漂移只产生警告，不阻止草案继续整理。发生内容冲突时不得接受新基线。

### 7. 主持对话审核

用户说“开始审核”“继续审核”“查看审核进度”或同义表达时，完整阅读 [对话审核规则](references/guided-review.md)，并先重建索引以获取 `reviewPlan`。

- “开始审核”：先用根引导说明整体范围；已有审核进度时明确询问是否从 `reviewPlan.next` 继续，不重复要求从头阅读。
- “继续审核”：直接进入 `reviewPlan.next` 指向的文档和审核组。
- 每轮只处理一个 UC 或单体需求，提出 1–3 个最重要的确认项；先给出可独立理解的简述，再提供准确文档链接。
- 允许用户回复“全部理解一致”“除功能点 N 外确认”“按推荐方案”“跳过”“稍后确认”“展开详细需求”或直接修正规则。
- 每次回答后立即按修订规则写回现有引导和详细需求，重建索引，再给出下一步；不要让审核进度只存在于聊天上下文。
- 用户暂停时返回已审核数量、待修改数量、未解决问题和下次继续位置。
- 不新增审核文档，不要求用户维护索引，不在本轮优化中生成或嵌入图表、流程图或 UI 图片。

## 修订已有需求

完整阅读 [修订规则](references/revision-rules.md)。

- 明确的用户修改直接写入详细需求，并把状态设为 `用户已确认`。
- 模糊建议只新增候选或问题，不改写已确认正文。
- 用户确认功能点只更新引导审核状态，不把关联需求自动改为 `用户已确认`；只有用户明确修正规则时才更新事实状态。
- 始终先更新详细需求，再同步公共规则、相关 UC、验收标准和引导文档。
- 用户直接编辑文件时，保留其文字；引导与详细需求冲突时，以详细需求为当前事实源，停止冲突部分的自动合并并报告。
- 重新抓取远端资料时先与 `_sources` 快照比较，不得覆盖用户已确认内容。
- 每轮修订更新文内修订记录，然后重建索引、刷新行号链接并重新校验。

## 交付

返回需求包根目录和三个入口：`00-需求引导.md`、详细需求入口、`requirement-package.json`。简要说明资料限制、UI 原始缓存完整度、文档数量、已确认项、冲突数、推断待确认数和信息缺失数；不输出技术实现建议。
