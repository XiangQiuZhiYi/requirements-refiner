# 对话式需求审核规则

## 1. 进入审核

收到“开始审核”时：

1. 重建索引并读取 `reviewPlan`、`reviewSummary` 和未解决问题。
2. 没有任何审核进度时，先指向根 `00-需求引导.md`，用 3–6 句话说明背景、本期范围、UC 数量和主要资料限制。
3. 已有进度时，先报告简短进度，再从 `reviewPlan.next` 继续，不要求用户重新阅读已确认 UC。
4. 根总览只确认整体理解，不逐条重复详细需求；随后进入最高优先级审核组。

## 2. 单轮输出格式

一次只处理一个 UC 或单体需求，保持以下顺序：

1. `本轮查看`：给出可点击的引导文档链接和 UC 名称。
2. `主体需求`：用一小段话说明参与者、操作、结果和关键边界，让用户不打开文档也能回答。
3. `需要确认`：最多列出三个问题或功能点，优先采用索引 `focusItems`。
4. `如何回复`：给出一条与本轮内容匹配的自然语言示例，例如“UC05 除问题 1 外，其余理解一致”。

不输出大段目录，不一次列出所有 UC 的全部问题，不要求用户使用固定命令格式。

## 3. 选题顺序

按 `reviewPlan.groups` 顺序推进。组内优先级：

1. `阻塞开发`的待确认问题。
2. `需要修改`的功能点。
3. `影响验收`的待确认问题。
4. `存在疑问`的功能点。
5. 可能未同步的功能点。
6. `未审核`的功能点；优先整 UC 批量确认，不逐点追问。
7. `可后补充`的待确认问题。

同一 UC 的问题尽量连续处理。当前 UC 尚有明确修改正在同步时，不跳到另一个 UC。

## 4. 用户回复处理

- 明确确认：批量更新当前 UC 或指定功能点为 `理解一致`。
- 明确修改：先更新详细需求、规则和验收标准，再同步引导；相关功能点设为 `需要修改`，修改完成后请用户复核。
- 疑问：将相关功能点设为 `存在疑问`，保留问题并说明影响。
- 回答审核问题：写回详细需求和验收标准，将问题设为 `已解决`、`已同步：是`。
- 跳过或稍后确认：不改变状态，在本次会话中继续下一项。
- 暂停：报告当前进度和下次入口，不继续提问。

每次落盘后运行构建和校验。引导与详细需求同步确认无误后才接受同步基线。

## 5. 完成条件

所有功能点均不再是 `未审核` 时，可以宣布“本轮功能审核完成”。同时单独汇总：

- `需要修改`和`存在疑问`的功能点。
- 尚未解决的阻塞开发、影响验收和可后补充问题。
- 可能未同步的功能点。

未解决问题可以继续保留，不得为了显示完成而自动确认。审核输出保持纯文本 Markdown；除非用户以后另行明确要求，不新增或嵌入图表、流程图、设计图或 UI 图片。
