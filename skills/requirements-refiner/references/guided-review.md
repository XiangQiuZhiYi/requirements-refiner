# 对话式需求审核规则

## 1. 进入审核

收到“开始审核”时：

1. 重建索引并读取 `reviewPlan`、`reviewSummary` 和未解决问题。
2. 没有任何审核进度时，先指向根 `00-需求引导.md`，用 3–6 句话说明背景、本期范围、UC 数量和主要资料限制。
3. 已有进度时，先报告简短进度，再从 `reviewPlan.next` 继续，不要求用户重新阅读已确认 UC。
4. 根总览只说明整体理解，不逐条重复详细需求；随后进入编号最靠前的未完成 UC。后续 UC 即使存在阻塞问题，也不跳过当前 UC。

## 2. 单轮输出格式

一次只处理一个 UC 或单体需求，保持以下顺序：

1. `本轮查看`：给出可点击的引导文档链接和 UC 名称。
2. `本 UC 包含的功能`：读取 `reviewPlan.next.features` 和引导正文，按功能点顺序列出全部功能名称及一句话行为说明。
3. `需要确认的问题`：先列出 `reviewPlan.next.pendingQuestions` 的全部问题标题和影响等级，再展开最多三个问题供用户回答。没有问题时明确写“当前没有待确认问题”。
4. `如何回复`：给出与本轮问题匹配的自然语言示例；不再要求用户逐个确认已经列出的功能点。

功能清单用于建立完整认知，不复制字段表和异常明细；只列当前 UC，不一次列出多个 UC，也不要求用户使用固定命令格式。

## 3. 选题顺序

按 `reviewPlan.groups` 的 UC 顺序推进：整体需求、UC01、UC02……。只有当前 UC 已完成或用户明确要求暂缓，才进入下一个 UC。组内优先级：

1. `阻塞开发`的待确认问题。
2. `需要修改`的功能点。
3. `影响验收`的待确认问题。
4. `存在疑问`的功能点。
5. 可能未同步的功能点。
6. `未审核`的功能点；优先整 UC 批量确认，不逐点追问。
7. `可后补充`的待确认问题。

同一 UC 的问题必须连续处理。当前 UC 尚有明确修改正在同步时，不跳到另一个 UC。

## 4. 用户回复处理

- 明确确认：批量更新当前 UC 或指定功能点为 `理解一致`。
- 明确修改：先更新详细需求、规则和验收标准，再同步引导；相关功能点设为 `需要修改`，修改完成后请用户复核。
- 疑问：将相关功能点设为 `存在疑问`，保留问题并说明影响。
- 回答审核问题：写回详细需求和验收标准，将问题设为 `已解决`、`已同步：是`；然后检查当前 UC 是否还存在未解决问题。
- 当前 UC 的全部问题都已解决并同步，且不存在`需要修改`、`存在疑问`或同步漂移：若用户未主动要求待确认，执行 `--complete-review-group <UC编号> --accept-guide-sync`，自动把该 UC 剩余`未审核`功能点设为`理解一致`。
- 当前 UC 一开始就没有待确认问题：列完功能清单后直接执行自动完成，并说明已确认；用户当场要求待确认时取消自动完成。
- 跳过、稍后确认或明确要求当前 UC 待确认：不执行自动完成，不伪造确认状态；根据用户意图暂停或继续下一 UC。
- 暂停：报告当前进度和下次入口，不继续提问。

自动完成只改变引导功能点的审核状态，不把详细需求事实状态改为`用户已确认`。命令存在未解决或未同步问题、待修改、疑问、同步漂移时必须失败。每次落盘后运行构建和校验。

## 5. 完成条件

每个 UC 自动完成后立即报告“UCxx 已全部确认”，并进入下一个未完成 UC。所有功能点均不再是 `未审核` 时，可以宣布“本轮功能审核完成”。同时单独汇总：

- `需要修改`和`存在疑问`的功能点。
- 尚未解决的阻塞开发、影响验收和可后补充问题。
- 可能未同步的功能点。

用户主动保留的待确认问题必须继续保留，不得为了显示完成而自动确认。审核输出保持纯文本 Markdown；除非用户以后另行明确要求，不新增或嵌入图表、流程图、设计图或 UI 图片。
