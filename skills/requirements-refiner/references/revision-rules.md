# 用户修订与同步规则

## 1. 判断用户表达

- `改为`、`确定`、`最终是`、`本期不做` 等明确表达：视为用户确认。
- `可能`、`考虑`、`是不是`、`我倾向于` 等不确定表达：保留为候选意见，不改写正式需求。
- 用户要求直接采用某段文字时，保留业务含义，可做语法和结构整理，不额外扩展规则。

## 2. 更新顺序

每轮修订按以下顺序处理：

1. 找到相关需求编号和来源。
2. 更新详细需求或公共需求，状态设为 `用户已确认`。
3. 检查同一规则影响的字段、交互、状态、权限、异常和验收标准。
4. 检查其他 UC 是否引用该公共规则。
5. 更新引导文档中的简明说明和审核问题。
6. 更新相关功能点的审核状态；仅确认理解时不得改变详细需求事实状态。
7. 追加修订记录，不覆盖历史记录。
8. 重建索引、刷新链接并执行校验。
9. 人工确认引导与详细需求一致后，使用 `--accept-guide-sync` 接受新同步基线。

不要只修改用户提到的一句话而遗漏关联规则。

## 3. 直接编辑文件

- 用户直接编辑详细需求：视为事实源变更，保留其文字，并同步派生内容。
- 用户只编辑引导文档：把新增答案或规则视为待同步输入，写回详细需求后再刷新引导。
- 引导与详细需求同时被修改且含义冲突：停止冲突部分自动合并，展示双方内容和受影响编号。
- 无法判断修改意图时，不覆盖任何一方。
- 用户说“整个 UC 确认”时，将该 UC 全部功能点设为 `理解一致`；“除功能点 N 外都确认”只批量更新未排除项。功能点存在明确修改意见时设为 `需要修改`，疑问表达设为 `存在疑问`。

## 3.1 对话审核回复

- 用户只确认“主体理解一致”时，批量更新当前审核组的功能点；未回答的审核问题保持待确认。
- 用户回答具体审核问题时，先把答案同步到详细需求和关联验收标准，再把问题设为 `已解决`、`已同步：是`。
- 用户说“按推荐方案”时，只有当前问题已经在对话中明确展示推荐内容和影响才可采用；否则先说明推荐方案，不得静默代选。
- 用户说“跳过”或“稍后确认”时不修改事实状态和审核状态，只在当前轮次移动到下一个项目；下次会话仍可重新出现。
- 用户要求“展开详细需求”时，只展示当前事项关联的需求编号和必要段落，不倾倒整份详细文档。
- 每次写回后重建索引；仍有下一审核组时主动继续引导，全部功能点已处理时汇总未解决问题，不强迫当场关闭可后补充项。

## 4. 来源刷新

重新获取语雀或 MasterGo 时，不直接重生成全部文档：

1. 对比 `_sources` 快照。
2. 将远端变化映射到需求编号。
3. 对 `来源已确认` 内容提出更新。
4. 对 `用户已确认` 内容只报告冲突，不覆盖。
5. 用户确认后更新正文、来源快照和修订记录。

## 5. 修订记录

每轮至少记录：版本、日期、修改内容、涉及编号、来源和操作者。使用原文件更新，不创建 `v0.1`、`v0.2` 文件副本。

版本建议：

- 初稿：`v0.1`
- 每轮需求确认：次版本递增，如 `v0.2`
- 关键缺口全部关闭后：`v1.0`
- 已形成基线后的需求变更：`v1.1`、`v1.2`
