# 需求文档契约

## 1. 事实层级

详细需求是唯一事实来源。公共需求是多 UC 场景下共享规则的事实来源。引导文档是派生的阅读视图，不独立定义业务规则。

每条需求只能使用以下状态：

| 状态 | 使用条件 |
|---|---|
| 来源已确认 | 语雀或 MasterGo 明确表达，且来源之间无冲突 |
| 用户已确认 | 用户明确补充、选择或修正 |
| 推断待确认 | AI 为暴露完整性缺口而提出的候选规则 |
| 来源冲突 | 两个来源对同一事实表达不一致 |
| 信息缺失 | 已知该信息开发或验收需要，但没有候选答案 |

不得使用“默认规则”“一般情况下”等措辞绕过状态标记。

## 2. UC 拆分

只按来源或用户明确给出的 UC 拆分。以下内容不能作为拆分依据：

- MasterGo 的页面、Frame、弹窗和抽屉数量。
- 一个页面上存在多个操作。
- AI 认为某段流程“像一个用例”。
- 为了让目录看起来均衡而进行的人工拆分。

来源明确多个 UC 时，保持其名称和顺序；来源编号缺失时可按出现顺序补 `UC01`、`UC02`，但不能改变边界。来源未明确 UC 时使用单体模板，并加入待确认问题。

## 3. 编号

阶段编号使用来源明确的顺序；“一期”对应 `P1`，“二期”对应 `P2`，未分期使用 `PX`。

编号前缀必须由当前需求包的阶段独立生成，不能从上一需求包或历史对话继承。目录阶段为“未分期”时，UC、单体、公共规则和审核问题均统一使用 `PX`。

- 功能需求：`P1-UC01-FR001`
- 业务规则：`P1-UC01-BR001`
- 验收标准：`P1-UC01-AC001`
- 未拆分 UC 的单体需求：`P1-REQ-FR001` 或 `PX-REQ-FR001`
- 公共规则：`P1-COM-BR001`
- 审核问题：`P1-UC01-Q001`、`P1-REQ-Q001` 或 `P1-COM-Q001`

编号一经发布不得因排序、移动文件或修改标题而重用。删除的编号只在修订记录中标记废弃。

## 4. 需求条目格式

每条 `FR`、`BR`、`AC` 使用独立锚点和标题：

```markdown
<a id="p1-uc01-fr001"></a>
### P1-UC01-FR001｜需求标题

- 状态：来源已确认
- 来源：[DOC-01-S003｜章节](../_sources/DOC-01.md#doc-01-s003)

需求正文。
```

`来源` 不得为空。没有来源时写 `无；缺失说明：...`，状态必须是 `推断待确认` 或 `信息缺失`。

直接来自语雀、设计图或用户补充的事实应链接到规范化快照中的稳定来源片段。片段编号使用 `DOC-01-S001`、`UI-01-S001`、`IMG-01-S001` 或 `USER-01-S001`。每个片段对应一个业务主题或不可拆分的事实组，不按每句话拆分，也不使用快照行号作为稳定定位。

## 5. 详细程度

详细需求覆盖实际存在或明确缺失的以下维度：

- 背景、目标、范围和非本期范围。
- 用户角色、权限和前置条件。
- 主流程、分支流程和完成结果。
- 页面、弹窗、抽屉及其进入和退出关系。
- 展示字段、输入字段、组件类型、必填、默认值、格式、校验和选项来源。
- 按钮触发条件、行为、成功反馈、失败反馈和禁用条件。
- 状态枚举、状态转换和不同状态允许的操作。
- 加载、空数据、无结果、失败、取消、重复提交和其他边界场景。
- 可验证的正常、异常、权限和边界验收标准。

只描述需求，不指定组件文件、状态库、接口路径或代码实现。

## 6. 引导文档

引导文档必须让审核者不打开详细文档也能理解主体需求，不得退化为目录。

单体需求由根目录 `00-需求引导.md` 承担完整引导。多 UC 需求必须拆为两级：

- 根引导：整体背景、目标、范围、跨 UC 流程、公共规则、UC 关系与每个 UC 的一段概述，并链接到对应 UC 引导。
- UC 引导：放在 `UCxx-名称/需求引导.md`，是用户审核该 UC 的主要入口。

每份 UC 引导至少包含：

- UC 的需求背景、目标、参与者、触发方式和完成结果。
- 能说明该 UC 如何使用的主要流程。
- 按“功能点 1、功能点 2……”逐项展开的需求阐述。
- 每个功能点的操作行为、关键规则、结果、审核重点及至少一个详细需求受管链接。
- 该 UC 的冲突、信息缺失和可直接回答的审核问题。

每个功能点紧随标题放置唯一受管标记，并在描述后记录审核状态：

```markdown
### 功能点 1：创建用户
<!-- guide-point:P1-UC01-FR001 sync:pending -->

管理员填写必要信息后创建用户，系统返回创建结果。

- 审核状态：未审核
- 关键规则：名称唯一。
- 参考详细文档：
  - <!-- req-link:P1-UC01-FR001 -->
```

功能点状态仅允许 `未审核`、`理解一致`、`需要修改`、`存在疑问`。`guide-point` 主编号取该功能点最主要的关联需求编号且不得重复；同一功能点可继续链接多个 FR、BR、AC。用户意见为空时不生成空字段。

整个 UC 的审核状态由功能点自动汇总，不增加需要用户维护的 UC 状态。根引导和 UC 引导只保留一行受管审核摘要。

功能点说明应介于一句话目录和详细规格之间：审核者能理解“做什么、何时做、结果是什么、最重要的限制是什么”，但不复制完整字段表、所有异常分支或全部验收用例。

### 6.1 引导文档强调样式

引导文档使用可移植的 Markdown 样式建立阅读层级：

- 重点样式主要用于“功能点说明”的需求描述正文，使用 `**加粗**` 突出业务对象、用户操作、选项、状态、数量限制、操作结果、权限边界和已经明确的结论。
- “关键规则”“审核重点”“参考详细文档”等固定标签保持普通样式，把视觉注意力留给功能描述本身。
- 来源冲突继续通过对应章节和状态表达，不使用比功能描述更强的额外样式抢占注意力。
- 一个自然段只突出真正影响理解的少量关键词，不加粗完整长句，不使用颜色、复杂 HTML 或仅靠图标表达含义。
- `来源冲突`、`推断待确认` 和 `信息缺失` 中的候选结论不能通过加粗伪装成已确认结论。

## 7. 审核问题

使用以下格式：

```markdown
### P1-UC01-Q001｜新用户是否立即启用

- 状态：待确认
- 影响等级：阻塞开发
- 关联需求：P1-UC01-FR001
- 用户答复：
- 已同步：否

请确认新用户创建成功后是立即启用，还是等待审核。
```

用户答复后，把状态改为 `已解决`、已同步改为 `是`，并将答案写入详细需求。仅勾选复选框不等于确认业务规则，除非问题明确给出唯一含义。

影响等级限定为：

- `阻塞开发`：影响范围、核心流程、数据归属或权限，必须先确认。
- `影响验收`：主体功能明确，但边界或结果尚不能准确验收。
- `可后补充`：文案、排序或非核心展示细节。

AI 负责首次分级，用户可以修正。缺少等级只产生警告，非法等级属于校验错误。

## 8. 同步检测

索引脚本对每个功能点链接的详细需求标题、状态、来源和正文计算指纹。首次生成自动建立基线；详细需求变化后基线保持不变并产生“可能未同步”警告。只有确认引导与详细需求一致后才能使用 `--accept-guide-sync` 更新基线。警告不得使草案校验失败。

## 9. 来源冲突

冲突项必须同时记录：

- 来源 A 的原意和定位。
- 来源 B 的原意和定位。
- 受影响的需求编号和验收范围。
- 用户需要做出的具体选择。

不得用“以设计稿为准”或“以文档为准”作为全局默认优先级。

## 10. 对话审核入口

根引导和 UC 引导在审核摘要下方保留一行轻量入口：用户可在聊天中输入“开始审核”或“继续审核”，由 AI 指引下一份文档。入口不是新的审核状态，也不创建新文档。

索引中的 `reviewPlan` 是由现有功能点状态、待确认问题和同步状态生成的派生数据。审核组严格按整体需求、UC01、UC02……排序，不允许后续 UC 因问题影响更高而插队。每组包含完整功能清单、未解决问题清单、最多三个本轮焦点，以及是否满足自动确认条件；组内仍按阻塞问题、需要修改、影响验收问题、存在疑问、同步漂移、未审核功能点、可后补充问题排序。

审核对话每轮只处理一个 UC 或单体需求，最多提出三个确认项。AI 必须先用简短自然语言说明主体需求和本轮为什么需要确认，再提供准确的引导或详细需求链接；不能只回复文件路径和问题编号。

“跳过”或“稍后确认”不得伪造已确认状态。用户暂停或离开后，后续对话重新构建索引，从仍未审核或待确认的内容继续。

## 11. 机器交接入口

需求包根目录必须生成 `requirement-package.json`，使用相对路径指向根引导、详细需求、`requirement-index.json` 和 `_sources/raw/UI-xx/manifest.json`。该文件只承载机器可读的交接信息，不增加用户审核步骤，也不复制需求正文。

UI 来源的规范化 Markdown 快照用于需求引用；完整原始缓存用于后续技术方案和开发。原始缓存状态只能是 `complete`、`partial` 或 `missing`。历史数据没有落盘时标记 `missing` 并说明原因，不得从摘要反向伪造原始 DSL。
